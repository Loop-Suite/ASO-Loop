# aso-loop Research & Evidence Survey (2026-08-01)

## 1. Overview

`aso-loop` is a Rust CLI that ports the `Loop-Suite/bizplan-loop` pattern — "generate N candidates → deterministic rule checks → LLM rubric scoring (de-anchoring) → feedback-driven regeneration" — into the ASO (App Store Optimization) listing-copy domain. The pipeline consists of `src/checks.rs` (deterministic checks: character count, keyword coverage, cross-field duplication, banned terms), `src/score.rs` (LLM rubric scoring: writing winning_conditions up front → requiring verbatim quotes from the source text → multi-round, multi-model trimmed-mean aggregation), `src/loop_run.rs` (the feedback-driven regeneration loop + a length-inflation canary), and `--gate-model` in `src/main.rs` (held-out re-scoring by a model that did not participate in the loop).

This document has two purposes.

1. Re-verify — **this time by directly opening the actual source files and primary sources** — the facts recorded as "confirmed" in the initial research round (the conclusion that semihcihan/App-Store-Optimization-CLI has no similar architecture, that furkancingoz/aso-skill was not reviewed, that fastlane deliver has no hardcoded constants, that the official Apple OpenAPI spec has no maxLength), and self-correct anything found to be wrong.
2. Newly investigate areas not yet covered — commercial AI copy agents, ASO applications of OSS agent frameworks (LangGraph/CrewAI), academic grounding for reward-hacking prevention, and final confirmation of Apple's character-limit rules.

The methodology follows the standard set by `research-loop` from the same organization: **do not draw conclusions from README/landing pages alone.** Every code-related statement below is the result of directly fetching and reading actual repository files (TypeScript/Python/Ruby/JSON) via `gh api`, with file paths, function names, and constant names left as citation evidence.

## 2. Re-verification of prior research (including self-correction)

### 2.1 semihcihan/App-Store-Optimization-CLI — "Does it have rule-checks + de-anchored LLM scoring + a held-out gate like ours?"

Initial conclusion: "No." This time the full repository tree of 302 files was fetched for re-verification.

- Running `grep -iE "openai|anthropic|gpt-|claude|llm"` over the full list of repository paths turns up exactly one match: `website/src/pages/llms.txt.ts`. This is an `llms.txt`-spec page meant for AI crawlers to read a site summary, not an LLM API integration.
- File names like `cli/services/prompts/aso-prompt-handler.ts` and `cli/dashboard-server/prompt-session.ts` are easy to misread as "there's LLM prompt-management logic here." Opening them shows they're actually `inquirer`-based **CLI interactive input** (taking Apple ID/password/2FA code input via `inquirer.prompt(...)`) — the `promptWithCliAsoPrompt()` function handles cases like `apple_credentials` and `verification_code`. Nothing to do with LLMs.
  **Self-correction note**: judging by file/directory names alone would have led to the wrong classification of "there's prompt-related code, so it must be LLM integration." This repository is itself proof of the principle that you have to actually open the files.
- The actual "evaluation" logic, `handleAsoEvaluateKeywords()` in `cli/mcp/services/aso-evaluate-keywords.ts`, is not an LLM judgment but a **numeric threshold filter** on `minPopularity`/`maxDifficulty` (constants `DEFAULT_MIN_POPULARITY = 6`, `DEFAULT_MAX_DIFFICULTY = 70`; it JSON-parses the output of the `aso keywords` subprocess and applies only a cutoff). No rubric, no scoring model, no regeneration.
- `cli/mcp/content/rules.md` is static markdown containing a summary of App Store Connect policy (IAPs can't be deleted, no emoji, etc.) that is merely exposed as an MCP resource — there is no loop anywhere in the code where an LLM scores against these rules.

**Conclusion (re-verification result = same as initial conclusion, no self-correction needed)**: this repository is a purely deterministic keyword research/difficulty-analysis CLI. The initial conclusion — that no LLM-judgment/regeneration loop exists in the codebase — was correct.

**Attribution re-confirmed**: directly read `normalizeKeyword()` (`keyword.trim().toLowerCase()`) and `sanitizeKeywords()` (dedup via `Set` after normalization) in `cli/domain/keywords/policy.ts`, and `normalizeTextForKeywordMatch()` (`.normalize("NFKC")` + `/[^\p{L}\p{N}\p{M}\s]/gu` substitution + lowercasing + whitespace cleanup) in `cli/shared/aso-keyword-utils.ts`. Re-confirmed code-to-code that aso-loop's `checks.rs::normalize_keyword`/`sanitize_keywords`/`normalize_text_for_match` port this logic accurately (100% consistent with the README's §Open-source attribution section; the README already correctly discloses the approximation gap from not using the `unicode-normalization` crate).

**Incidental finding**: `ASO_MAX_KEYWORDS = 100` in `cli/domain/keywords/limits.ts` is a cap on **the number of keywords allowed per API call**, an entirely separate constant unrelated to Apple's keyword-field character limit (100 characters). Since the numbers happen to coincide, this is an easy point of confusion, revisited in §3.4.

### 2.2 furkancingoz/aso-skill — "How much does the architecture overlap with ours?"

The initial round only checked the license (NOASSERTION) and did not reference the code. This time, `agents/aso-full.md`, `agents/aso-quick.md`, `commands/aso-build.md`, and `lib/keyword_engine.py` were read directly.

- Structure: 3 Claude Code subagents (`aso-full` = opus model, `aso-quick`, `asc-api`) + 8 commands (`/aso`, `/aso-build`, `/aso-connect`, `/aso-assets`, etc.) + a Python library (`keyword_engine.py`, `asc_api.py`, `rank_tracker.py`, `screenshot_composer.py`, `searchads_api.py`).
- Reading `aso-full.md`'s 4-phase workflow (research → optimize → launch → improve) shows **one generation per field, single pass**. The "Validation Checklist" looks like:
  ```
  - [ ] Title ≤ 30 chars ✓
  - [ ] Subtitle ≤ 30 chars ✓
  ```
  — this is a **prompt instruction telling the LLM to self-mark the checklist**, not deterministic code that actually counts string length the way aso-loop's `checks.rs` does. This repository has no code at all (Rust/TS/Python or otherwise) that validates the generated output. `KeywordEngine` in `lib/keyword_engine.py` is a research engine that classifies keyword relevance/competition/priority — not a scorer for generated copy.
- The only thing close to a "loop" is `<iteration_protocol>` in `aso-quick.md` (around lines 205-230 of the file): after generation, it shows the user a menu:
  ```
  1. 🎨 Tone: [more professional | casual | premium | playful]
  2. 🎯 Focus: [specific feature to emphasize]
  3. 🔑 Keywords: [add/remove specific keywords]
  4. ✏️ Rewrite: [specific field to regenerate]
  5. 💾 Save: [store to memory and finish]
  ```
  and regenerates **only the field the user explicitly selects** ("Single field update: regenerate only that field"). This is human-triggered manual rewriting, not an automatic self-improvement loop with a target score, termination condition, and scoring model.
- `lib/keyword_engine.py` has the following hardcoded constants: `APPLE_TITLE_LIMIT = 30`, `APPLE_SUBTITLE_LIMIT = 30`, `APPLE_KEYWORD_LIMIT = 100`. This is reused in §3.4 (Apple character-limit uncertainty) as an observed instance of "the common pattern of third-party SDKs just hardcoding 100 without distinguishing characters from bytes."

**Conclusion**: no scoring loop confirmed at the code level. The only overlap with aso-loop is the surface-level goal of "generating copy per store field" — deterministic rule checks, an LLM rubric, de-anchoring, and a held-out gate are nowhere in this repository. **No architectural overlap.**

### 2.3 fastlane/fastlane (deliver module) — "No hardcoded character-count constants; delegated to the App Store Connect API"

The initial conclusion was verified in three layers this time: (a) re-checking the source, (b) downloading the full official App Store Connect OpenAPI spec and exhaustively searching for `maxLength`, (c) real-user GitHub issues.

- Grepping `deliver/lib/deliver/upload_metadata.rb` (827 lines) turns up only numeric literals unrelated to character counts, such as `limit: 2` (retry count) and `time_in_ms / 1000`. There are no 30/100/170/4000-style character-limit constants.
- The only place "100" appears in `deliver/lib/assets/summary.html.erb` (the upload-result summary HTML template) is the CSS value `width: 100%`.
- Searching the entire `fastlane/fastlane` repository for the `keywords`+`100` combination via GitHub code search (`search/code`) turns up nothing in validation logic (aside from the one report-template HTML hit).
- Directly downloading the official OpenAPI spec mirror for the App Store Connect API (`EvanBacon/App-Store-Connect-OpenAPI-Spec`, `specs/latest.json`, updated 2026-06-23, 6.68MB, 1,337 JSON Schema definitions) and exhaustively searching it in Python found **zero occurrences of the string `maxLength` in the entire spec**. The `keywords` property on `AppStoreVersionLocalizationCreateRequest`/`UpdateRequest`, and the `name` (title)/`subtitle` properties on `AppInfoLocalizationCreateRequest`, are all plain `{"type": "string"}` with no length constraint whatsoever at the schema level. This round's verification is more rigorous than before (the previous round checked only a single schema; this time zero matches were confirmed across the full 6.68MB spec).
- Reading fastlane GitHub issue [#16226](https://github.com/fastlane/fastlane/issues/16226) ("Add length and character checking to metadata precheck", closed) shows the actual error message a real user received during the `fastlane release` upload step, quoted in the issue:
  > "App Name must not contain control characters ... **Subtitle can't contain more than 30 characters.** Subtitle can't contain more than 30 characters. ..."

  This message was **returned by the App Store Connect server at upload time, not by fastlane's code** (the very fact that the issue title is a feature request — "ideally this kind of violation should surface earlier, at the precheck stage" — reconfirms, via a real user report, that fastlane currently has no client-side pre-validation). Incidentally, this also confirms that the Apple server's own error message uses the word "characters" (reused in §3.4).

**Conclusion (no self-correction, higher confidence)**: the initial research was accurate. Confidence was raised this time via two independent primary sources: (i) a full-spec grep and (ii) a real-user issue.

### 3.2 ASO applications of OSS agent frameworks (LangGraph/CrewAI)

Investigated via GitHub repository search (`aso+langgraph`, `aso+crewai`, `app-store-optimization+agent`). No LangGraph-based ASO-specific flagship project of meaningful size was found (only generic LangGraph awesome-list repos matched). On the CrewAI side, found `Dilshan189/agentaso` (★1, no license) and read `main.py` directly.

- Architecture: a **fully sequential, single-pass pipeline** binding 4 `Agent`s (`researcher`, `copywriter`, `marketing_strategist`, `ui_ux_designer`) via `Crew(process=Process.sequential)`. Tasks run in the order `research_task → writing_task → marketing_task → design_task`, each executing exactly once, with no back-edge (review → rewrite).
- `writing_task`'s `description` contains the phrase `"3 App Title Options (max 30 characters each)"`, but this is **only a prompt instruction given to the LLM**. `tools.py` defines only one tool, `ASOScraperTool`, and there's no code that scores or validates the generated output — there's no way to catch it even if the LLM exceeds 30 characters.
- Critique/rewrite agent, rubric, score, termination condition, held-out verification — none of these exist.

**Conclusion**: exactly the same pattern research-loop confirmed in the sources of GPT Researcher/company-research-agent/MetaGPT ("a sequential pipeline of generation stages, no rebuttal or re-measurement") is observed identically in a CrewAI implementation in the ASO domain. `Dilshan189/agentaso` is a small ★1 project, so its representativeness is limited (no larger, more mature LangGraph/CrewAI-based ASO-specific project was found in this research round). The furkancingoz-style "Claude/Cursor Agent Skill" format repositories found during the search (e.g. `Eronred/aso-skills`, ★1697, not separately verified) are single-pass skills structurally similar to §2.2 rather than graph-based frameworks, so they were excluded from this §3.2 scope (graph-based multi-agent frameworks) — left as a §5 backlog item. For the question "does an ASO pipeline with discourse/reward-hacking-prevention structure exist in the OSS agent-framework ecosystem," the only direct evidence found this round answered **"no."**

### 3.3 Reward-hacking prevention in de-anchoring/LLM-as-judge — additional academic grounding

Found 2 new papers that **do not overlap** with the literature already cited by `bizplan-loop`'s `DESIGN.md` (12 items, which the aso-loop README explicitly states it "inherits the same grounding from") — TrustJudge, Rulers, Prometheus, "More Convincing Not More Correct", Meta-Rewarding, Length-Controlled AlpacaEval, "LLMs Cannot Self-Correct Reasoning Yet", Self-Refine, "Nine Judges Two Effective Votes", PoLL, MT-Bench, "Who Validates the Validators?", "Pairwise or Pointwise?".

- **[Scaling Laws for Reward Model Overoptimization](https://arxiv.org/abs/2210.10760)** (Gao, Schulman, Hilton; OpenAI, ICML 2023) — this paper trains a "proxy reward model" on data labeled by a "gold-standard reward model" (playing the role of a human), optimizes a policy against that proxy, and quantitatively measures **how the gold-RM score and proxy-RM score diverge**. Whether via RL optimization or best-of-n sampling, as optimization against the proxy continues, gold-standard performance stalls or reverses past some point while the proxy score keeps climbing — this is exactly the **prototype** of the phenomenon a held-out gate is meant to detect. aso-loop's `--gate-model` is an implementation that approximates this paper's "gold RM vs proxy RM" setup as "loop-participating judge (proxy) vs non-participating judge (gate)."
  - **[Uncertainty/limitation, self-flagged]**: Gao et al.'s gold RM is a benchmark designed (conceptually, even if in a synthetic experimental setting) to represent "true" preference. aso-loop's `--gate-model` is merely **another LLM proxy**, not a gold reward — the mere fact that the two proxies are different models does not mean reward hacking is "detected"; only that "a disagreement between two proxies is observed." This distinction is not accurately reflected in the warning text in `report.rs::write_loop_report` ("suspected scorer optimization (reward hacking)") — **strictly speaking it is "disagreement between scorers," not a direct measurement of "disagreement with actual copy quality," so the wording is somewhat overstated/exaggerated.** (Improvement proposed in §4, §5)
- **[Correlated Proxies: A New Definition and Improved Mitigation for Reward Hacking](https://arxiv.org/abs/2403.03185)** (Laidlaw, Singhal, Dragan; UC Berkeley, ICLR 2025) — formally defines reward hacking as "the correlation coefficient r between proxy reward and true reward over the state-actions the reference policy encounters," and theorizes how this correlation collapses as optimization proceeds. Shows that regularizing the χ² divergence of the occupancy measure is theoretically more effective than KL regularization against the reference policy.
  - Implication: `loop_run.rs` currently does not regulate "how much the document changed from the previous one" at all during each regeneration round (there is a length canary, but no content-drift regularization). Applying Correlated Proxies' logic directly, the more sharply the document changes each round to raise the judge score (i.e., the more it drifts to fit the "plausibility" pattern the judge has learned), the greater the risk that its correlation with actual quality breaks down — this grounds the backlog addition of **a metric that measures round-to-round similarity and warns on excessive drift** (§5).
- **Re-applying prior knowledge (FacTool, Loki) to the ASO domain**: revisiting FacTool's (GAIR-NLP, [arXiv:2307.13528](https://arxiv.org/abs/2307.13528)) core principle — "verify via actual tool-based execution/lookup, not the LLM's own judgment" — reconfirmed that **`checks.rs` is itself already an ASO-domain implementation of this principle**. Character count (`chars().count()`), keyword coverage (`normalize_text_for_match` string matching), and banned terms (`Regex::find`) are all handled by deterministic code, not LLM judgment — this wasn't articulated with reference to FacTool during initial design, but it's the same principle in hindsight. What FacTool newly suggests is **a blind spot not yet covered**: as the README's "Limitations" section already states, "if a factual claim in `--brief` is wrong, it carries straight through into the copy, and that copy can still pass scoring" — checks.rs does not address this at all. The "check-worthiness identification" stage of Loki's ([arXiv:2410.01794](https://arxiv.org/abs/2410.01794)) 5-stage pipeline (selecting only claims worth verifying, not every sentence) could cheaply fill this blind spot — there's room to add a deterministic (or rule+LLM hybrid) second-pass check that first uses regex to **screen for quantitative/factual claims only** (e.g. "100k+ downloads", "#1/first/only in the industry") rather than the whole copy, then cross-checks only those sentences against the brief (§5).

### 3.4 App Store Connect character limits — final confirmation

Previous round: confirmed as far as "no maxLength in the official OpenAPI spec." This time: (a) re-searched the full spec (already done in §2.3, re-confirmed zero hits across the full spec — cross-referenced rather than duplicated), (b) collected additional hardcoded constants from third-party SDKs, (c) retried access to Apple's official HTML documentation.

- **OpenAPI spec**: already confirmed in §2.3 — zero occurrences of the string `maxLength` across the entire spec (1,337 schemas). The properties corresponding to keywords/title/subtitle are all unconstrained plain strings.
- **Third-party hardcoded constants, a 2nd instance obtained**: `lib/keyword_engine.py` in `furkancingoz/aso-skill` (§2.2) hardcodes `APPLE_KEYWORD_LIMIT = 100`, `APPLE_TITLE_LIMIT = 30`, `APPLE_SUBTITLE_LIMIT = 30` as Python constants, with no comment distinguishing characters from bytes. Care is needed regarding `semihcihan/App-Store-Optimization-CLI`'s `ASO_MAX_KEYWORDS = 100` (§2.1), which is a **limit on keyword count per API call, not a character count** — an easy optical illusion. Actually opening both third-party sources reconfirmed that "the number 100 shows up everywhere, but nowhere is it specified whether that's a character basis or a byte basis."
- **Retried access to Apple's official HTML documentation**: retried `developer.apple.com/help/app-store-connect/...`, `.../documentation/appstoreconnectapi/app-store-connect-api-release-notes`, etc. via WebFetch, but **these are JS-rendered pages, so static content could not be retrieved** (only an empty body was returned). This research round also failed to directly quote the original text of Apple's official pages — this is "not confirmed," not "does not exist" (a browser-rendering-capable tool is needed; recorded as a limitation of this round's toolset — §5 backlog).
- **Indirect primary source (new)**: the **actual App Store Connect server error message** quoted in fastlane GitHub issue [#16226](https://github.com/fastlane/fastlane/issues/16226) — `"Subtitle can't contain more than 30 characters."` — the server itself refers to its own unit as "characters." This is one step more official (an actual server response string) than the "Apple Developer Forum 705360 (a case of 100 Thai characters passing)" cited in the previous round, but it still has the limitation of being **a user-captured error-message quote, not primary official documentation**.
- **Conclusion (unchanged, only confidence raised)**: the aso-loop README's current wording — "likely character-based (given the server error message's word choice + the case of 100 Thai characters passing + no byte constraint stated in the OpenAPI spec), but not confirmed via 100% official primary documentation" — **remains accurate.** This research round only added one more piece of evidence (the "characters" wording in the server error message); no counter-evidence emerged to change the conclusion. It is correct to keep the README's `[uncertain]` tag and its recommendation to "verify directly in App Store Connect" as-is.

## 4. Overall conclusions

- **Deterministic rule-checking + LLM rubric scoring, by itself, is common.** furkancingoz/aso-skill claims something similar in the form of a "checklist," and AppTweak Atlas AI in the form of a "Relevancy Score." Claiming "we're the only one" based on this alone would be wrong.
- **The differentiator is the combination and rigor, not any individual element.** (1) de-anchoring, which requires writing winning conditions before regeneration, (2) a score cap of 60 when there's no verbatim quote, (3) multi-model, multi-round trimmed-mean aggregation, (4) held-out re-scoring by a model that didn't participate in the loop, (5) a length-inflation canary — no case with **all 5** of these was found in this round of research (2 OSS re-verifications + 1 new OSS + 2 commercial + academic research). In particular, not even commercial tools mentioned a held-out gate at the level of public documentation.
- **However, this conclusion is "not found," not "does not exist."** Commercial tools (Atlas AI, Jenova AI) are closed-source, so code-level disproof is fundamentally impossible, and no flagship ASO-specific project was found on the LangGraph side, leaving the CrewAI sample effectively a single project (★1) — carrying the same degree of sample limitation as research-loop drawing conclusions from a single company-research-agent case.
- **A point warranting self-skepticism (newly found)**: as noted in §3.3, `report.rs`'s held-out warning text flatly asserting "suspected reward hacking" is somewhat exaggerated. Under Gao et al.'s framework, aso-loop's gate-model is "another proxy," not a "gold reward," so a held-out disagreement is a signal of "an improvement that doesn't reproduce across two scorers," not direct measured evidence of "an actual drop in copy quality." This distinction is worth reflecting more clearly in the README/report wording.
- **That `checks.rs` is already an ASO-domain version of FacTool-style tool-augmented verification** is a new perspective gained from this research round. It wasn't articulated with that intent during design, but in hindsight, the principle "don't just trust values the LLM self-reports (character count, keyword inclusion, banned terms) — re-verify them with code" is exactly FacTool's core claim. However, **brief-to-copy factual-consistency verification remains a blind spot where this principle has not yet been applied** (§3.3, §5).

## 5. Proposed next steps (backlog)

In priority order.

1. **[P1] Correct the held-out gate warning text.** Soften `report.rs::write_loop_report`'s "suspected scorer optimization (reward hacking)" wording to something more accurate, like "disagreement between scorers (an improvement that doesn't reproduce with a different proxy)." In the README's "held-out gate" section, cite Gao et al. (arXiv:2210.10760) / Correlated Proxies (arXiv:2403.03185) and state the limitation that "the gate-model is also just another proxy, not a gold reward."
2. **[P2] Brief-to-copy factual-consistency check (applying FacTool/Loki).** Add a check to `checks.rs` that "flags it when a quantitative claim not present in the brief (download count, ranking, awards, etc.) appears in the copy." Referencing Loki's check-worthiness identification stage, start with deterministic first-pass filtering via regex/patterns (number+unit, "#1/first/official"-style terms), and apply LLM judgment only to sentences that pass the filter, to control cost.
3. **[P2] A round-to-round drift metric (applying Correlated Proxies).** Add to `loop_run.rs` a measurement of document similarity between rounds (e.g. token Jaccard similarity, achievable without adding an external crate) to warn on sharp drift — detecting, separately from the length canary, cases where "the content changed into completely different copy, yet only the score went up."
4. **[P3] Retry obtaining Apple's original documentation text.** This round again failed to access the JS-rendered pages (a WebFetch limitation) and could not directly quote developer.apple.com's official HTML — retrying with a browser-automation-capable tool (e.g. Playwright MCP) might secure the grounds to remove the `[uncertain]` tag.
5. **[P3] Black-box benchmarking of commercial tools.** Code verification is impossible since they're closed-source, but feeding the same brief into Atlas AI/Jenova AI's free tiers and black-box testing the actual output's character-count accuracy and keyword-reflection quality could empirically compare "real-world quality versus ours" (this research round was limited to documentation research).
6. **[P3] Periodically re-survey the LangGraph/CrewAI landscape.** No representative project was found this round, but since this is a fast-moving ecosystem, it's worth repeating a search like "aso langgraph/crewai" in the next round to check for new entrants. At the same time, the "Claude/Cursor Agent Skill" format repositories excluded from this round's scope (e.g. `Eronred/aso-skills`, ★1697 — likely structurally similar to furkancingoz/aso-skill but unverified) are also worth checking at the code level someday.
